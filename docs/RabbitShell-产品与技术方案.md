# RabbitShell 产品与技术方案 v0.1

日期：2026-11-02。阶段：方案设计，尚未开始产品实现。

> 文档状态：早期探索初稿，保留作为讨论参考。其中工作区布局、菜单和操作规则已有多轮调整，当前以 [RabbitShell 交互设计检查清单](RabbitShell-交互设计检查清单.md) 为准。本文提出的技术路线、框架与扩展功能均不代表用户已经确认；技术选型仍待后续讨论。

## 1. 产品定位与设计前提

**一个以远程工作区为中心的 SSH 桌面工具，将终端、文件管理、轻量编辑、服务器监控与端口转发放在同一处。**

从用户提供的 ShellX 截图可确认：连接管理器支持分组、搜索与配置导出；主窗口包含连接标签、终端、独立命令输入区、命令历史、本地/远程双栏文件列表、传输任务，以及 CPU、内存、进程、网络、延迟和磁盘信息。截图只能作为功能和布局参考，不代表已验证其内部实现。

RabbitShell 保留这些日常运维能力，同时采用 VS Code Remote SSH 的操作模型：**选择主机 → 连接 → 打开远程目录 → 在该目录中编辑和执行命令 → 下次恢复工作区。**

暂定前提：Windows 桌面优先，远端 Linux 优先，中文界面，个人开发者或小团队使用，主要任务是配置修改、服务维护、日志检查与文件发布。macOS、本地 Linux、远端 Windows/BSD 作为后续适配，不算首版已支持。

## 2. 三个核心对象

| 对象 | 保存的内容 | 示例 |
| --- | --- | --- |
| 主机连接 Host | 地址、用户、端口、认证引用、跳板机、主机指纹、分组与环境标签 | staging-api |
| 远程工作区 Workspace | 一台主机 + 一个远程根目录 + 打开文件、布局、常用命令及端口配置 | staging-api:/srv/update-service |
| 会话 Session | 当前运行的终端、SFTP 通道、转发和监控订阅 | shell-1、日志终端 |

一个主机可保存多个工作区。一个工作区只对应一台主机；全局标签可以打开不同主机的多个工作区。所有命令和文件操作都绑定明确的 workspaceId/sessionId，切换标签不能把旧命令发送到新主机。

恢复工作区意味着恢复目录、标签、草稿和布局，并重新建立连接；不代表恢复已断开的远端进程。需要跨断线保留程序时，再提供显式启用的 tmux 模式。

## 3. 界面与操作方式

### 3.1 主界面结构

- 顶部：工作区标签和全局命令入口。每个标签显示主机别名、目录和连接状态。
- 最左侧活动栏：连接、远程文件、传输、监控、设置。
- 左侧边栏：连接树或远程目录树；服务器指标默认显示摘要，完整监控按需展开。
- 中央：可分组的终端和文件编辑标签。
- 底部：终端、双栏文件传输、任务、端口等可切换面板。
- 状态栏：主机、环境、当前目录、连接状态、编码和任务数。

采用深色/浅色主题、中文优先、清楚的图标和键盘操作。边栏和底部面板可调整尺寸并保存，不把所有信息固定挤在一屏。

### 3.2 两种布局预设，共用同一个工作区

**终端布局，默认。** 中央大终端，底部按需显示本地/远程双栏文件管理，左侧连接与状态摘要。最接近截图，适合运维与发布。

**目录布局。** 左侧远程目录树，中央文件编辑器，底部终端；传输和监控切换展示。适合像 Remote SSH 一样打开项目、修改配置和执行命令。

切换布局只改变面板排列，保留终端、打开文件与未保存内容。不要实现成两个独立产品或两套会话。

### 3.3 连接流程

1. 从连接树、最近工作区或命令面板进入；支持输入 `ssh user@host -p 22` 创建连接表单。
2. 支持手工填写和导入 `.ssh/config`。导入先展示解析结果及不支持的配置，保留来源；修改默认写入应用配置，不自动覆盖原始 SSH 配置文件。
3. 首次连接展示主机指纹，用户信任后保存；已知主机的指纹变化时中止自动连接。
4. 连接成功后直接可开终端，并提供“打开远程文件夹”和最近目录。
5. 从最近工作区进入时直接打开其目录；认证过期则显示清楚的重新认证入口。

连接过程显示“解析配置、连接跳板机、连接主机、认证、打开工作区”等实际阶段；认证错误与网络中断分别处理，避免无限重试。

### 3.4 日常工作流程

- 点击远程文件 → 在编辑器打开 → 修改 → Ctrl+S 写回远端 → 显示保存结果。
- 目录右键“在此处打开终端” → 新终端从所选目录启动。
- 终端目录与文件树可显式定位联动；默认不强制同步。可靠的自动目录跟随依赖可选 shell integration/OSC 7 等机制，不解析提示符猜目录，不在用户交互终端偷偷执行探测命令。
- Ctrl+Shift+P 打开命令面板；Ctrl+P 查找当前已索引/已加载文件，完整远程搜索后续增强；Ctrl+` 聚焦或切换终端。
- 原始 PTY 终端直接接受输入。截图中的独立命令输入框改成可折叠“命令编辑器”，用于多行命令、历史和模板；只有明确发送才执行，焦点不同的 Enter 行为需要明确。
- 常用命令先定位到目标主机和工作目录，再执行；首版不默认广播到多台机器。
- 添加端口映射后展示本地地址、远程目标、状态与停止按钮；本地地址被占用时提示选择其他端口。
- P1 增加“在 VS Code 中打开此远程目录”：检测本地 VS Code 与 Remote SSH 扩展，使用双方可识别的 SSH 主机别名打开相同目录。应用内保存的密码和连接状态不能直接等同于 VS Code 的认证配置；需要明确提示缺失的外部配置。

### 3.5 截图场景的完整闭环

打开 `staging-api:/srv/update-service` → 编辑 `public/android/version.json` → 保存成功 → 在该工作区终端运行维护命令 → 查看结果和资源变化 → 上传或下载相关文件 → 关闭后保留工作区记录。

方案和界面草图仅使用示例主机与模拟数据，不连接截图中的服务器，也不执行截图中的命令。

## 5. 推荐技术架构

### 5.1 技术选择

| 层 | 推荐方案 | 原因与边界 |
| --- | --- | --- |
| 桌面外壳 | Electron | Windows 交付成熟，Node 生态易于集成 SSH、文件与凭据处理；代价是安装体积和内存 |
| 界面 | React + TypeScript + Vite | 适合复杂面板、状态隔离和长期维护 |
| 终端 | xterm.js | 处理 ANSI、输入与终端显示；远端 shell 由 SSH PTY 提供 |
| 编辑器 | Monaco Editor | 配置文件编辑体验成熟；不等于获得 VS Code 的扩展和远程语言服务 |
| SSH/SFTP | ssh2，放在独立连接进程 | 一个协议栈提供 PTY、exec、SFTP 和端口通道，降低首版复杂度 |
| 本地数据 | SQLite + 版本化迁移 | 保存连接元数据、工作区、任务和偏好；不存明文凭据 |
| 凭据 | Electron safeStorage + 操作系统保护；按需接入凭据库 | Windows 优先利用系统加密，认证数据只在后端解密 |
| 发布 | electron-builder 等成熟打包工具 | 先交付 Windows 安装包，公开发布阶段补签名和更新验证 |

本地终端若进入范围，再用 node-pty。远程终端本身不需要本地 PTY；xterm.js 与 SSH PTY 通道之间传输字节及 resize 事件。

不优先选择直接分叉 VS Code：它会带来扩展宿主、远端 Server、发行版维护和许可梳理。Tauri 适合对体积有严格要求的版本，但团队需要承担 Rust 后端和跨 WebView 调试成本；当前阶段 Electron 路线更集中。

### 5.2 进程与模块边界

```text
React 渲染进程
  工作区 / xterm.js / Monaco / 文件视图 / 监控视图
             │ 白名单、带类型的 IPC
Electron 主进程
  窗口 / 数据库 / 凭据 / 本地文件 / 生命周期
             │ 进程间消息
连接与任务进程
  SSH 适配器 / 会话管理 / SFTP 队列 / exec / 隧道 / 采样
             │ SSH 加密通道
Linux 服务器
  sshd / SFTP / 用户 shell / 系统指标
```

渲染进程关闭 Node 集成、开启隔离，不接触私钥和任意命令执行接口。IPC 绑定工作区和会话标识，校验参数，限制可访问的本地文件范围。SSH 大流量和文件任务避免阻塞 UI。

主机配置可复用，但工作区和任务的状态必须隔离。多个通道可共用 SSH transport；大量文件传输需要并发限制、队列调度，必要时使用额外连接，避免拖慢终端响应。

## 6. 与 Remote SSH 的关系及兼容性边界

VS Code 官方说明：Remote SSH 会在远端安装 VS Code Server，以提供远程扩展和开发体验。RabbitShell 第一版借鉴其“连接主机、打开目录、远程编辑和执行、端口转发、恢复工作区”的操作方式，通过 SSH/SFTP 实现基础能力，不要求常驻远端服务。

**操作体验相似，不代表首版完整复刻 Remote SSH 的底层能力或 OpenSSH 的所有配置。**

`ssh2` 不会自动理解全部 OpenSSH 配置。应实现独立的配置解析与能力检查层，首批验证 `Host`、`HostName`、`User`、`Port`、`IdentityFile`、常见 `Include` 和单跳 `ProxyJump`，遵循支持范围内的 Host 匹配及配置优先级。验证通过一项再列为支持。

`ProxyCommand`、`Match exec`、PKCS#11、安全密钥、复杂证书和部分系统 agent 行为不能静默忽略；遇到这些配置要展示具体不支持项和解决入口。尤其不能在导入配置时自动运行其中的外部命令。

Windows OpenSSH agent 命名管道、加密私钥以及跳板组合是技术验证重点。若用户的现有工作流强依赖完整原生 OpenSSH，则在实现前将原生 OpenSSH 后端提升为主路线，连同 SFTP 子系统、凭据交互、转发和进程生命周期一起验证；不能只换终端实现就声称其他功能同样兼容。不要假定 Windows 支持与 Unix 相同的连接复用能力。

为未来替换协议后端保留 `SSHAdapter` 接口，但首版只交付一套验证过的实现，避免同时维护两套能力不同的连接引擎。

如果需要完整代码补全、调试与扩展，优先通过“在 VS Code 中打开”接入现有开发环境。该功能作为独立集成，不把 VS Code Server 当作 RabbitShell 可直接复用的通用远端协议。

## 7. 需要提前设计好的可靠性

### 7.1 远程文件编辑与传输

- 读取时保留内容基线及远端元数据，保存前检查远端是否发生变化；发生冲突时提供重新加载、对比或明确覆盖。
- 优先在同一目录写临时文件，成功后使用服务端支持的重命名方式替换；原子覆盖与元数据保持受服务器扩展和文件系统影响，必须探测能力。
- 处理符号链接、所有权、权限、磁盘满、只读目录及跨文件系统情况；不能把“替换文件”当作始终无副作用。
- 基础 SFTP 检查无法保证所有并发写入场景的原子 compare-and-swap。对于高频多人修改文件，应明确限制，后续通过受控服务端机制或工作流解决，不能承诺零竞争窗口。
- 未保存草稿按用户配置本地保护；连接断开不清空编辑器。
- 文件列表按需加载，传输流式处理，限制并发。取消后记录已传输进度，清理行为有明确规则。
- P0 的“重试”可以重新传输，不能宣传成断点续传。后续续传需要验证源文件一致性、偏移与目标状态。

### 7.2 连接与重连

- 明确区分未连接、连接中、待认证、已连接、重连中和失败。
- 网络断开时退避重试；认证失败、指纹变化和权限拒绝需要明确操作，不盲目循环。
- 重连可重新建通道和恢复界面，旧 shell 中的进程是否存活由服务器及会话机制决定。
- 保存端口映射配置不意味着程序启动时无提示地重新监听所有地址；默认绑定本机回环地址，并展示运行状态。
- 命令历史不保证自动识别所有秘密，提供关闭记录、按主机禁用和清理入口；凭据、终端输出不进入普通诊断日志。

### 7.3 监控开销

只对已连接且用户关注的主机采集。Linux 先使用专用 exec/采样通道读取 `/proc` 与必要系统命令；不占用用户终端。活动视图参考 3–5 秒刷新，后台放慢或暂停，进程列表按需刷新。

CPU 与网络速率使用相邻采样差值；连接延迟与网络吞吐分开标注。命令不可用或权限不足时显示不可用及原因，不显示伪造的 0。首版不宣称统一支持所有类 Unix 系统。

## 8. 本地数据模型与建议目录

核心表：`hosts`、`credential_refs`、`workspaces`、`workspace_layouts`、`session_snapshots`、`transfer_jobs`、`port_forward_profiles`、`known_host_keys`、`command_presets`。快照保存恢复所需描述，不序列化活的 socket 或远端进程。

建议代码边界：

```text
src/
  main/          Electron 生命周期、凭据、本地文件、持久化
  preload/       受限 IPC 接口
  renderer/      React 工作区与面板
  connection/    SSHAdapter、连接管理、SFTP、隧道、指标
  shared/        类型、事件与参数校验
tests/           连接、传输、断线及界面集成验证
docs/            产品范围、兼容矩阵、交付记录
```

| 技术验证 | 3–5 工作日 | Windows 密钥/agent/跳板连接、PTY resize、SFTP、大文件吞吐、断线和主机校验；记录配置兼容矩阵 |
| 工作台骨架 | 1–2 周 | 可安装桌面壳、连接树、工作区、稳定终端、多标签、可恢复布局 |
| 文件与编辑 | 2–3 周 | 双栏文件、传输队列、文本编辑、冲突处理、草稿和基础恢复 |
| 监控与稳定性 | 1–2 周 | 基础指标、端口转发、错误反馈、长时间运行、安装升级验证 |

一个日常可用的 Windows MVP 参考约 5–8 周；原生 OpenSSH 全兼容、跨平台、公开发行质量会明显增加工作量。先交付端到端的一个工作区，再扩展功能数量。

## 10. 验收标准

1. 在受控 Linux 环境中完成密码、普通/加密密钥、首批确认支持的 agent 和跳板连接；不支持的配置有明确解释。
2. 首次主机指纹被确认后可连接，指纹变更会阻断连接，不静默放行。
3. 多终端输入、中文、vim/top 等交互程序、窗口缩放和 Ctrl+C 正常；持续输出不会使 UI 失去响应。
4. 两个主机工作区来回切换时，文件、终端和端口映射始终归属正确主机。
5. 上传/下载后通过校验确认文件一致；覆盖、取消、权限拒绝、磁盘满和网络中断有可理解结果。
6. 两个客户端先后修改同一配置文件时，能发现已发生的远端变更并提供冲突处理；额外记录并发写入边界。
7. 关闭再打开后恢复工作区与草稿；不把新的 shell 误标为原有进程已恢复。
8. 端口转发验证本机监听范围、端口冲突处理及断开后清理。
9. 监控数值与同时间段系统工具对照，采集失败与零值可区分。
10. 在记录硬件、服务器和网络条件的前提下测量启动、内存、终端延迟与文件吞吐；技术验证后再定具体性能门槛。

## 11. 当前建议与待验证假设

建议先确定“终端默认、目录布局可切换”的主界面，以 Windows + Linux、免常驻远端 Agent、个人本地使用作为首版范围。启动开发前最值得核实的是实际 SSH 配置复杂度、是否必须远端代码补全/调试、以及是否存在强制轻量安装包要求；这些会影响底层路线。
